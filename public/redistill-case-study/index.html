Redistill: Engineering a Redis-Compatible Database for Single-Instance Performance

Posted on Sep 21, 2026

Redistill is a high-performance, in-memory key-value database that speaks the Redis protocol. It is designed for teams that use Redis-compatible clients for latency-sensitive caching workloads but want substantially more throughput from each server.

Designed and built entirely by Shahid Shaikh, Redistill covers the database engine, Redis protocol implementation, persistence, operational controls, packaging, documentation, and performance engineering.

  • Published throughput: 9.07M operations per second on one AWS c7i.16xlarge instance
  • Published latency: 0.479 ms p50 and 1.215 ms p99
  • Relative throughput: 4.5× Redis and 1.7× Dragonfly in the documented single-instance benchmark
  • Implementation: Rust, Tokio, DashMap, sharded storage, zero-copy buffers, and batched I/O

The problem

Redis is frequently placed directly in the hot path for sessions, API caching, counters, and rate limiting. As traffic grows, a single-threaded server can require additional instances and operational coordination even when the workload is fundamentally cache-oriented.

Redistill explores a focused question: how much throughput and latency improvement is possible when a Redis-compatible cache is designed around modern multi-core hardware from the beginning?

The goal is not to reproduce every Redis feature. It is to provide a smaller, production-oriented surface for workloads where predictable latency, high per-instance throughput, and compatibility with existing clients matter most.

Architecture and engineering decisions

Use all available cores

Redistill runs on Tokio and distributes connection and command processing across the machine rather than funneling work through one execution thread. This lets a single process use contemporary high-core-count servers effectively.

Reduce shared contention

The in-memory store uses DashMap with 2,048–4,096 shards. Lock-free reads and fine-grained write coordination keep unrelated keys from competing for one global lock.

Keep the network path small

Zero-copy buffers, pipelined command processing, and batched I/O reduce allocation and system-call overhead. These decisions are especially important under high connection counts and deep pipelines, where seemingly small per-command costs compound quickly.

Preserve the Redis integration model

Redistill implements RESP, so existing tools and clients—including redis-cli, redis-py, ioredis, and go-redis—can connect without an application-specific protocol adapter. Supported functionality includes core string and hash commands, TTLs, scanning, authentication, server information, and health monitoring.

Make durability optional

The fastest cache configuration keeps persistence disabled. For workloads that need recovery across restarts, Redistill also supports RDB snapshots and append-only files with configurable synchronization. Teams can choose the durability cost appropriate for each deployment.

Measured results

The published competitive benchmark used an AWS c7i.16xlarge instance with 64 CPU cores and 128 GB of memory. Redistill, Redis, and Dragonfly were tested with memtier_benchmark using the same client configuration:

  • 60-second test duration
  • 8 threads and 160 connections
  • Pipeline depth of 30
  • 256-byte values
  • 1:1 SET to GET ratio
  • Random key access
  • Persistence disabled across all systems

Under that workload, Redistill recorded 9.07M operations per second, 1.58 GB/s of bandwidth, 0.479 ms p50 latency, and 1.215 ms p99 latency. The repository includes the raw benchmark results, and the documented command can be rerun on other hardware.

These figures describe a specific, pipeline-heavy, single-instance benchmark. They should be evaluated against an application’s own value sizes, command mix, durability settings, client behavior, and latency objectives.

Operational readiness

Performance alone is not enough for a production service. Redistill also includes:

  • Password authentication and TLS support
  • Memory limits and configurable eviction policies
  • Connection limits and connection-rate controls
  • Health endpoints and Redis-compatible INFO statistics
  • Graceful shutdown behavior for orchestrated environments
  • Docker, Homebrew, binary, and source-based installation paths

When Redis remains the better fit

Redistill is deliberately optimized for focused cache and key-value workloads. Redis remains the better fit when a system requires:

  • Native replication or clustering
  • The full Redis data-type surface, including lists, sets, sorted sets, streams, or pub/sub
  • Drop-in compatibility with commands outside Redistill’s documented feature set
  • An established Redis operational ecosystem as a stronger requirement than per-instance performance

Redistill currently scales horizontally through client-side sharding or a compatible proxy; native clustering remains outside its present feature set.

Outcome

Redistill demonstrates that a focused Redis-compatible design can deliver substantially higher single-instance throughput while retaining familiar clients and operational interfaces. Just as importantly, it documents the workload, limitations, and architectural tradeoffs behind the headline numbers so teams can decide whether those tradeoffs match their own systems.
